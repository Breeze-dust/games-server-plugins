## 1. 项目是什么

一个 Paper 服务端（Minecraft 26.2 / Java 25，端口 25560，`online-mode=false`）上跑**多款小游戏**，
共用一个主城。插件分三层：

```
MiniGameLib（公共库：Chat / SetupMode / WaitCountdown / PlayerStats / HubAPI）
    ↑
HubCore（主城：菜单、tab 分区、游戏注册表、回主城道具）
    ↑
9 款小游戏：GuessTheBuild(建筑猜猜乐) DuelArena(单挑) TntRun HotPotato(烫手山芋)
           MurderMystery(密室杀手) SkyPit(天坑) FootballArena(绿茵足球) ColorParty(色盲派对)
           BuildRun(你建我跑)
外加 GameWorlds（多世界管理，负责建/加载 world_xxx 并套用世界规则）
```

**依赖方向**：小游戏 → MiniGameLib → HubCore。**改了 MiniGameLib 或 HubCore，所有游戏 jar 都要一起重传。**

**玩家记录**：7 个小游戏的战绩/击杀/第一名/玩家名统一写在唯一文件
`server/plugins/MiniGameLib/players.yml`（读写入口 `com.hub.data.PlayerStats`，详见 `docs/玩家记录.md`）。

## 2. 改东西去哪里

| 要改的东西 | 文件 |
| --- | --- |
| 各游戏玩法/事件 | `<游戏>/src/main/java/.../`（先看该插件 README 的速查卡） |
| 主城菜单/tab/游戏注册 | `HubCore/src/main/java/com/hub/` |
| **主城菜单的布局/物品/提示** | 不用改代码：游戏里 `/hub menu edit`（`/hub menu help` 看命令），落盘在 `server/plugins/HubCore/config.yml` 的 `menu` 段 |
| 公共能力（Chat、等待倒数、配置模式工具、玩家记录） | `MiniGameLib/src/main/java/com/hub/`（`util/`、`data/`） |
| 跨插件调用接口 | `MiniGameLib/.../api/HubAPI.java` + `HubService.java`（HubCore 实现） |
| 世界规则（pvp/难度/怪物…） | `server/plugins/GameWorlds/config.yml` |
| Paper 世界设置（爆炸击退等） | `server/config/paper-world-defaults.yml` |
| 编译依赖清单（加了新依赖要改） | `paper-classpath.ps1`（build.ps1 与 check-stats.ps1 共用） |

## 3. 构建 / 部署 / 预检 / 打包

```powershell
# 编译全部 11 个插件（产物 .build\out\）
D:\BuildBattle\build.bat
# 只编一个（自动带上依赖的 MiniGameLib / HubCore）
D:\BuildBattle\build.bat -Only SkyPit
# 编译并复制到 server\plugins\
D:\BuildBattle\build.bat -Deploy

# 本地预检：语法/关键配置/jar 指纹（上传前跑一下，能拦掉一整类问题）
powershell -ExecutionPolicy Bypass -File D:\BuildBattle\verify.ps1
# 玩家记录自检：迁移 + 合并写盘（改了 PlayerStats 或战绩相关代码必跑）
powershell -ExecutionPolicy Bypass -File D:\BuildBattle\check-stats.ps1
# 打包上传（自动把玩家记录快照到 backups\ 并排除出压缩包；压缩包根 = 服务端根）
# ★默认连 cache\ versions\ libraries\（Paper 的下载缓存，约 169 MB）一起传，面板才不会重新
#   Downloading mojang_26.2.jar / Applying patches；不带就加 -SkipRuntime
D:\BuildBattle\pack-upload.bat
# 也可以直接跑脚本（开关更多）：
powershell -ExecutionPolicy Bypass -File D:\BuildBattle\pack-upload.ps1 -WithWorlds
# 单独存档 / 恢复玩家记录（换服、把面板记录拿回本地）
powershell -ExecutionPolicy Bypass -File D:\BuildBattle\players-backup.ps1 -Action Save
# 一键快照整个 server\ 成单个 zip（换服/整机搬家前的保命备份；恢复 = 停服后解压回 server\ 覆盖）
# 进包：world\ server.jar plugins\ config\ cache\ versions\ libraries\ 及所有 *.yml / *.json
# 只跳过 jdk\（本机 Windows JDK，面板自带 Java）、logs\、world_backup_*；-Slim = 回到只带源码/配置
# 玩家记录 plugins\MiniGameLib\players.yml 不进包，只快照进 backups\players-<时间>.yml（和 pack-upload.ps1 一个套路）
D:\BuildBattle\server-backup.bat
```

**面板上传铁律**：先停面板服 → 再覆盖 → 再启动。不能只传 `plugins/*.jar`，
`config/`、各插件的 `config.yml / data.yml / words.yml / arena-*.snap`，
以及 Paper 的下载缓存 `cache/ versions/ libraries/` 都要在
（`data.yml` 现在只用于首次自动迁移，之后记录都在 `plugins/MiniGameLib/players.yml`）。

## 4. 硬性约定（踩过的坑，别重犯）

1. **`.ps1` 必须是纯 ASCII**（PS 5.1 无 BOM 时按 ANSI 读，中文注释会直接导致语法错误）。
2. **YAML 的 `键: 值` 冒号后必须有空格**。`detective-stone-seconds:90` 会让整份配置加载失败
   （Bukkit 会给插件一个空配置 → 表现为"场地全没了"）。`verify.ps1` 会检查。
3. `gamehub:` 这个命名空间**不要改名**（写在各插件 kit 存档的物品数据里）。
4. 插件数据目录 = `server/plugins/<插件名>/`，改配置要连线上那份一起改（源码里的 `resources/config.yml` 只是模板）。
5. 关服时这些插件会 `saveAll()` 回写配置：`MurderMystery / SkyPit / TntRun / DuelArena / HotPotato`
   （GTB 不写）。所以运行中上传会被关服时的旧内存覆盖。
6. **同优先级事件拦截必须限定自己的世界**（最贵的一课，详见 `docs/已知坑.md` §1）。

## 5. 已知坑（症状 → 根因）

**完整表格已移到 [`docs/已知坑.md`](已知坑.md)**（含"本地行、面板不行""爆炸不推人""进服刷『你不在任何场中』"
"菜单点了没反应""选场地菜单空白/颜色不对"等全部条目 + 怎么确认）。

遇到以下情况，**先读那份文档，再改代码**：

- 本地好、上传面板就坏（同一份代码）；
- 某个游戏"没有场地/装备是旧的"；
- 上传了配置但没生效；
- 主城菜单点了没反应、场地羊毛颜色/名字不对；
- 选场地菜单点进去一个物品都没有。

## 6. 排查协议（省 token 的关键）

1. **先要证据，再改代码。** 一句日志、一段配置、一个文件大小，胜过我猜三轮。
   游戏里能直接拿到证据的例子：`/paper version`、`/gw list`、`/team list`、`/plugins`、控制台日志行、
   `/hub games`（游戏显示名的权威名单）、`/hub arena desc`。
2. **不确定的机制，去服务器 jar 里读字节码**（`javap -c`），别凭记忆：
   例子：`ServerLevel.isPvpAllowed()` 读的是 gamerule；`WindCharge.explode()` 先看 `ExplosionPrimeEvent`；
   `ServerExplosion` 里那个 `disableExplosionKnockback` 只对玩家生效。
3. **找不到原因就加一行诊断日志**（临时 jar，只打日志不改功能），一次就能定位。
   例：Duel 里那段 `[风弹诊断]` 就是干这个的（定位完成后已删）；下次定位完记得删。
4. **超过两轮没定位到，就换"要证据"**，不要继续猜。

## 7. 改动纪律

- **一次只做一件事**，明确说"只改 X，别动别的"；改完给出：编译结果、部署的 jar 与**字节大小**、
  以及**验证方法**（涉及玩家记录再加 `check-stats.ps1` 的结果）。
- 涉及游戏规则的歧义（比如"误伤怎么算"）先问清楚再动手。
- **结论要落盘**：写进对应插件的 `README.md` 速查卡 / `docs/已知坑.md` / `docs/改动记录.md`，
  不要只留在对话里——下次会话只认仓库文档。
- **接入新小游戏时**：按 `HubCore/docs/游戏插件接入指南.md` 接好之后，照现有插件 `README.md`
  的速查卡格式给它写一张（职责 / 入口 / 命令 / 配置 / 玩家记录命名空间 / 常改文件 / 验证方法 / 未确认），
  以后改它的人（包括 AI）就不用读源码了。
- 做完一件事就收尾。

### 会话怎么切（省 token 的关键）

**同一插件、同一功能、还在调试同一件事 → 留在原会话；换了插件/换了主题/这件事已收尾 → 新开会话。**

| 继续原会话 | 新开会话 |
| --- | --- |
| 同一个 bug 的"改→验证→再微调" | 换到另一个游戏插件 |
| 同一插件的相邻小改动（文件已经读过） | 上一件事已完成并写进文档 |
| 下一步依赖刚才的改动 | 会话超过约 20 轮，或发现我在重复读同一文件/反复问同样的事 |
| | 上一轮结论已被"自动压缩"掉细节（这时请开新会话并让我重读文档） |

成本对比：新会话启动约 **2k token**（`AGENTS.md` + 目标插件的速查卡 + 按需读一节文档）；
而一个很长的会话里，单轮就要带上几万 token 的历史 —— 所以**新主题常常比硬撑在旧会话里更便宜**。
